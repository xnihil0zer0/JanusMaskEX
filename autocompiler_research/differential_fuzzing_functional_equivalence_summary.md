# Academic Paper Summary: A Differential Fuzzing-Based Evaluation of Functional Equivalence in LLM-Generated Code Refactorings

* **Title:** A Differential Fuzzing-Based Evaluation of Functional Equivalence in LLM-Generated Code Refactorings
* **Authors:** Simantika Bhattacharjee Dristi and Matthew B. Dwyer (University of Illinois Urbana-Champaign)
* **Venue:** Proceedings of the 2026 LLMTrust Workshop (co-located with FSE 2026)
* **arXiv ID:** [2602.15761](https://arxiv.org/abs/2602.15761)

---

## 1. Core Problem & Motivation
Large Language Models (LLMs) are increasingly used to perform code refactoring (e.g., optimizing code, translation between languages, changing design patterns). However, ensuring that the refactored code is **functionally equivalent** (behaviorally identical) to the original code is a major challenge.

Existing evaluations of LLM-generated refactorings rely on:
1. **Static Test Suites:** Running pre-existing test suites (e.g., HumanEval, MBPP). These tests are typically sparse and fail to cover boundary conditions, leading to false confidence.
2. **Syntactic Similarity (BLEU, CodeBLEU):** Comparing text structure, which does not guarantee semantic correctness.

Dristi and Dwyer address this by proposing **Eq@DFuzz**, an automated differential fuzzing framework designed to dynamically verify functional equivalence by exposing both the source and refactored code to a large, randomly generated input space.

---

## 2. Methodology & Architecture (Eq@DFuzz)

The Eq@DFuzz workflow follows a structured pipeline:
1. **Signature Extraction:** The tool extracts the function name, parameter list, and type annotations from the original source code.
2. **Strategy Generation:** Using the type annotations (e.g., Python type hints), Eq@DFuzz automatically maps types to corresponding **Hypothesis** strategies (e.g., generating integers, strings, nested lists, dictionaries).
3. **Differential Execution:**
   * The generated inputs are executed on the **original** function to establish "ground truth" outputs.
   * The same inputs are executed on the **refactored** function.
4. **Behavioral Equivalence Check:** The outputs (return values, exceptions, and mutations) of both executions are compared:
   * **Equivalence:** If the outputs match exactly across all test cases.
   * **Semantic Divergence:** If there is any discrepancy in return values or if one raises an unhandled exception while the other does not.

---

## 3. Key Findings & Results
The authors evaluated six state-of-the-art LLMs (GPT-4o, Codestral, CodeLlama, StarChat2, Qwen-2.5, Olmo-3) across three Python datasets (HumanEval, MBPP, APPS).

* **High Bug Injection Rate:** LLMs have a significant tendency to alter program semantics. **19% to 35% of refactorings** generated by LLMs were functionally non-equivalent to the original code.
* **Test Suite Inadequacy:** Traditional test suites are poor oracles. Approximately **21%** of the semantically non-equivalent refactorings went completely undetected by standard test suites, meaning they passed the tests but failed under differential fuzzing.
* **Common Failure Modes:**
  * **Boundary Cases:** Failure on empty inputs (like `[]` or `""`), large numbers, negative bounds, or special characters.
  * **Loop & Conditional Errors:** Slight alterations in index boundaries (e.g., `<` vs `<=`) or loop termination conditions.
  * **Exception Handling:** Refactored code raising unexpected `IndexError` or `ValueError` on inputs that the original function processed safely.

## 4. Relevance to JanusMaskJR (Agentic Compilation)
The findings and methodology of this paper are critical for JanusMaskJR:

1. **Defense Against LLM Hallucinations:**
   * JanusMaskJR uses LLM agents to rewrite, compile, and harden code.
   * Since LLMs inject wrong-code bugs in up to 35% of transformations, we **cannot trust** LLM-generated refactorings or compiler optimizations without dynamic validation.
   * Implementing an Eq@DFuzz-like pipeline is mandatory to verify every rewrite agent's output.
2. **Automating Oracle Verification:**
   * By automatically converting TypeScript/Python type annotations of functions under test into Hypothesis/fast-check strategies, JanusMaskJR can auto-generate the testing harness for differential fuzzing.
3. **Catching Silent Failures:**
   * Simple unit tests are not enough. Differential fuzzing provides the necessary coverage to catch the 21% of subtle bugs that slip past standard test suites, ensuring absolute behavioral equivalence in the compiled output.
