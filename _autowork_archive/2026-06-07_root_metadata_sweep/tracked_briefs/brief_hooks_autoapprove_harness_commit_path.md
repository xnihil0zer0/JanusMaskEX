# Title

Make the widened (autowork.enabled) auto-approve path able to actually COMMIT non-deny harness/** files (two gate gaps block every Phase-2 child)

# Scope

The Phase-2 unattended build is blocked because a `harness_plumbing` task that creates a NEW non-deny harness/** file (e.g. `harness/symbol_ledger.py`) is REJECTED on the auto-approve commit path even though `autowork.enabled: true` and `auto_approve_sensitive_harness: true`. Empirically reproduced 2026-06-05 dispatching `symbol-ledger-module`: ledger rows `auto_approve_ro_gate_failed` then `apply-path scope violation ... requires meta_task_type=harness_self_fix + operator approval (got meta_task_type='harness_plumbing', approval_ok=False)`. Root cause is TWO independent gate gaps on the SAME path; fix BOTH:

GAP 1 — `_enforce_apply_scope` ignores the widened posture. `harness/git_integration.py:43 _enforce_apply_scope` unconditionally rejects any harness/**, config/**, scripts/** rel-path unless `meta_task_type == 'harness_self_fix' AND approval_ok` (git_integration.py:72-77). But `harness/orchestrator.py:2047 _auto_approve_sensitive_eligible` (B0) DELIBERATELY DROPS the harness_self_fix meta requirement when `autowork.enabled` is truthy (orchestrator.py:2101-2104 — "WIDENED: auto-approve ANY harness/** path not on the irreducible _NEVER_AUTO_APPROVE deny-list ... Drops the self-heal-only gates (harness_self_fix meta + HMAC provenance + ceiling) so the daemon runs fully unattended"). So B0 grants `approval_ok=True` for a `harness_plumbing` non-deny harness/** write under widened mode, but the downstream `_enforce_apply_scope` STILL hard-rejects on `meta_task_type != 'harness_self_fix'`. The two gates disagree; B0's documented intent is defeated. FIX: thread the widened posture into `_enforce_apply_scope` so that, when widened auto-approve granted the apply (a non-deny harness/** rel-path with `approval_ok=True`), the meta_task_type==harness_self_fix requirement is RELAXED — i.e. accept the commit on the SAME irreducible-deny-list + approval_ok boundary B0 uses. The deny-list (`_NEVER_AUTO_APPROVE` / `_SENSITIVE_APPLY_GLOBS` membership for the never-auto set) and the membership check (rel ∈ files_touched) MUST remain enforced unchanged. The strict floor (autowork.enabled false/absent) MUST be byte-identical to today (still require harness_self_fix + approval).

GAP 2 — `auto_approve_ro_gate` fails closed for legitimate commits. `harness/git_integration.py:1584 _verify_from_ro_parent` extracts the PARENT commit via `git archive --format=tar <parent_head_sha>` into a throwaway tmp dir (NO `.git`, NO venv, NO editable install, NO conftest plugin resolution) and runs the THREE fixed `_RO_GATE_TESTS` (orchestrator.py:2270 = test_sec_inv2_trustroot.py, test_p10b_denylist_widen.py, test_replication_clean_room_static.py) there with `staging_path` prepended to PYTHONPATH, requiring pytest exit 0. Those three tests are GREEN in a normal checkout (verified: 14 passed, 1 skipped) but ERROR in the bare tarball because they need a real git repo / the full project environment, so `_verify_from_ro_parent` returns False and the gate refuses the apply (orchestrator.py:2780-2787). With `auto_approve_ro_gate: true` (currently set) this refuses EVERY auto-approve commit, not just unsafe ones — a fail-closed-on-environment bug, not a real security refusal. FIX: make the RO-parent verification run the trusted gate tests in an environment where they can actually execute green (re-init a git repo in the tmp checkout, or run the gate tests against the staging worktree using the parent-snapshot TEST BODIES copied in — preserving the "trusted test body, candidate module-under-test" property the docstring promises — or otherwise distinguish a genuine assertion failure from an environment/collection error and only refuse on a genuine failure). The anti-evasion property (a candidate cannot weaken its own copy of a gate test) MUST be preserved.
