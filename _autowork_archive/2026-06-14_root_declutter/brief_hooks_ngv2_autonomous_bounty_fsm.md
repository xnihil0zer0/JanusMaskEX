# Title

Autonomous bounty lifecycle as a deterministic state machine for NobleGreedv2 — drive the whole loop, from sourcing a bounty to hunt, to finding a bug in a repo, writing a PoC, performing a live test, verifying it, and assembling a turn-in-ready submission package, fully autonomously, with the ONLY human action being the final act of turning the bug in.

# Scope

Build, into the external NobleGreedv2 repo (working_dir /home/xnihil0zer0/NobleGreedv2), a deterministic finite-state-machine layer that orchestrates the complete bug-bounty lifecycle. The existing session machine (ngv2.state_machine.HuntStateMachine, PHASES=('hunt','triage','poc','detonate','report','done'); ngv2.session_api.SessionApi; ngv2.session_gate.gate_transition; ngv2.session_db.SessionDB; ngv2.detonation; ngv2.dedup; ngv2.fp_filter; ngv2.contracts) is the spine to EXTEND, not replace. The unifying architecture — identical to the rest of NobleGreedv2 — is: the FSM and every transition gate are PURE, stdlib-only, deterministic functions over INJECTED seams; all real-world non-determinism (network, LLM, subprocess scanners, real exploit execution, platform I/O) lives behind owner-hand-authored adapters injected at runtime, exactly as ngv2.poc_runner_live.py is the hand-authored live runner behind the injected runner seam. Correctness is enforced by withholding and checking, never by prompting.

The lifecycle to model, as an explicit FSM with one gate per transition:

- source -> hunt: a SOURCING + QUALIFICATION gate. Given a candidate target (repo/package) and an injected bounty_oracle seam (returns payout, open-submission count, days-since-last-audit, scope), a pure qualify(target, oracle_result) admits the target only when expected_payout > 0 AND open_submissions < saturation_cap AND days_since_audit >= freshness_min AND it does not match a pre-hunt false-positive-risk filter. Mirrors the legacy bounty_gate.py + qualify_target.py (GO/SKIP/UNKNOWN). Output: a qualified target_spec the existing hunt phase consumes.
- hunt -> triage: unchanged existing hunt (injected finders) producing Findings, then FP-filter + dedup (existing ngv2.fp_filter.filter_findings, ngv2.dedup.filter_new).
- triage -> verify: a GROUNDING/CONFIDENCE gate — the heart of the verification procedure. A pure compute_confidence(finding, signals) assigns a tier in (CONFIRMED, HIGH, MEDIUM, LOW) from a stack of INJECTED verifier signals (pattern/semgrep match, FP-filter verdict, symbolic/AST-constraint check, taint-flow proof, formal-path proof). The deterministic rule (from legacy grounding.py): a single tool match => MEDIUM; cross-validated independent agreement and clean FP-filter => HIGH; a structural taint-flow or formal-path proof OR a confirmed live PoC => CONFIRMED; a known-FP match => LOW. The transition gate admits only CONFIRMED/HIGH onward to poc; MEDIUM routes to a manual-review holding state; LOW is recorded as false-positive evidence and dropped. No silent drops — every routed finding is logged with its tier and the signals that produced it.
- verify -> poc -> detonate: existing PoC build (injected poc_builder) and live detonation (injected live runner). The detonate gate requires a semantic_verdict-grade 'confirmed' (exit 0 AND success marker AND expected filesystem-signature in the live fs diff) — i.e. it depends on the strengthened ngv2.detonation gate from the prerequisite brief ngv2_fix_detonation_semantic_gate; marker-spoofing alone must NOT confirm.
- detonate -> novelty: a NOVELTY/DEDUP gate. A pure classify_novelty(finding, known_corpus) over an injected corpus of prior submissions/advisories returns NOVEL / POSSIBLE_DUP / CONFIRMED_DUP (title + CWE + file-locus match). Only NOVEL (or an explicitly operator-overridden POSSIBLE_DUP) advances; CONFIRMED_DUP terminates the finding. Mirrors legacy novelty_checker.py.
- novelty -> report: existing report build, extended into a platform-shaped SUBMISSION PACKAGE (title, CWE, severity, vulnerable code refs, attack scenario, PoC reference, live-test evidence, impact, suggested fix) following the legacy submission report template.
- report -> awaiting_submission: a SUBMISSION-READINESS gate. A pure readiness(finding, poc, live_report, novelty, bounty) admits a package to the human only when ALL hold: confidence in (CONFIRMED, HIGH); a live_tested PoC with verdict 'confirmed'; novelty == NOVEL; bounty-eligible target; report package complete (readiness_score == 3). Anything short halts in a not-ready state naming exactly the missing artifact.
- awaiting_submission -> submitted: THE SINGLE HUMAN CHECKPOINT. The FSM parks a fully-assembled, turn-in-ready package in awaiting_submission and advances to submitted ONLY through an injected human-approval seam (an operator decision, analogous to JanusMaskJR's decision-file gate). Every prior transition is autonomous; this one, and only this one, requires a human. The actual act of turning the bug in on the bounty platform is the human's; the system's job is to make the package and the audit trail submission-ready and to record the outcome (ledger row) once approved.
- submitted -> done: terminal; persist the submission record (target, CWE, severity, payout-estimate, novelty, evidence, approval, timestamp via injected now_fn).

Decompose this into child briefs — one buildable pure module + its state-machine/gate wiring + its committed oracle per FSM stage (suggested children: source/qualify gate; grounding/confidence gate; novelty gate; submission-package builder; readiness gate; human-checkpoint approval gate; the extended PHASES/ALLOWED_TRANSITIONS + session_gate.gate_transition evidence gates wiring it all together; and a SessionApi/MCP surface extension exposing the new phases). You decide the actual child set and their build order; sequence by holding briefs back until their dependencies land (the gates feed each other source->...->submitted). Each child is pure, stdlib + ngv2 only, deterministic, with non-determinism injected, and is admitted only against a hand-authored RED oracle that drives the real module.

# Non-Goals

This epic is a decomposition only and integration is out of its own scope — it writes child briefs, it does not itself build code or author integration/e2e tests. The children build the deterministic FSM and pure gates ONLY; they MUST NOT implement the side-effecting adapters behind the injected seams — the real bounty-platform/huntr client, the semgrep/joern/codeql subprocess runners, the LLM hunt worker, and the real exploit-execution runner are owner-hand-authored irreducible-trust adapters (like ngv2.poc_runner_live.py) and are explicitly out of bounds for pipeline synthesis. Do NOT automate the actual submission turn-in to any live bounty platform — the human performs that; the system stops at a turn-in-ready package gated by the human-approval seam. No network, no live API calls, no real credentials, no wall-clock, no randomness in any built module; every clock/IO/model/network dependency is an injected parameter. Do NOT modify the irreducible/owner-only modules or rewrite the existing HuntStateMachine spine; extend it additively. Do NOT weaken any existing acceptance gate.
