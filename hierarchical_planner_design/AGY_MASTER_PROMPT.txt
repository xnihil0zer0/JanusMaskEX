WHAT IS BEING DESIGNED (read carefully — this is the feature the reports must scope)
============================================================
JanusMaskJR turns a "brief" (a markdown spec) into a "plan" (a DAG of tasks),
then dispatches each task to a DUAL-MODEL (Claude + Gemini) differential
synthesis pipeline that auto-commits validated code. Today the planner is FLAT:
one brief -> one DAG of leaf tasks. There is no planned hierarchy.

We are adding a HIERARCHICAL PLANNER with PLAN DECOMPOSITION, in three levels:

  - LEVEL 0 (exists, manual): a human authors the top-level decomposition by hand.
  - LEVEL 1 (the near-term build): a brief can be tagged "epic". An epic brief is
    blind-drafted by BOTH models into a set of CHILD BRIEFS (not leaf tasks),
    reconciled (dual-model agreement MUST hold at the decomposition layer too,
    or we recreate the bug this project exists to fix), and each child brief
    re-enters the EXISTING planner unchanged. One automated layer of hierarchy.
    Child briefs carry FROZEN INTERFACES authored at decomposition time into
    their spec.interfaces, and sibling ordering via the existing `dependencies`
    DAG — so cross-child symbol contracts are STATIC TEXT, not runtime state.
  - LEVEL 2 (the hard tier, later): fully recursive (child briefs spawn
    grandchildren) PLUS the runtime cross-cutting machinery: an interface/symbol
    REGISTRY/LEDGER that flows produced symbols/signatures downward across
    subtrees, a PARENT/CHILD-AWARE COMPLETION LEDGER (a parent epic is "done"
    only when all descendants verify), and FAILURE PROPAGATION (a failed
    grandchild fails its epic without deadlocking siblings), plus
    recursion-depth budgets to prevent infinite decomposition.

The reports must scope the COMPLETE system (all of Level 1 AND Level 2), with
concrete file:line anchors, so a downstream session can compile an ordered
implementation sequence from them.

PIPELINE CONSTRAINTS — every proposed change MUST be tagged with its viability

The harness builds ITSELF through its own pipeline, which can reliably land only
certain change shapes. For EVERY change a report proposes, tag it with one of:
  - [GREEN single-symbol]  one top-level function/assignment, <=~150 lines,
    applied as a single-symbol partial-edit. ~85% reliable. PREFERRED.
  - [GREEN new-file]       one brand-new single-file module. ~80% reliable.
  - [YELLOW multi-symbol]  touches several top-level symbols / multi-file. 60-70%,
    often must be SPLIT into multiple single-symbol briefs.
  - [RED class-method]     edits a method body inside an existing class (dotted
    Class.method qualname). ~0% reliable — the synthesis layer AST-fails on these.
    Must be re-shaped (new top-level helper the method calls, or whole-class
    replacement) or flagged as a mandatory HAND-EDIT.
  - [RED nested]           deeply nested try/except edits. Deterministic failure.
  - [HAND] pure config/declarative (requirements, ini, small consts) — trivially
    hand-landed, no value in routing through the pipeline.
Also note for each change: does it need an ORACLE-FIRST failing test (new files
and behavior changes do); and whether it touches the protected harness/ path.
