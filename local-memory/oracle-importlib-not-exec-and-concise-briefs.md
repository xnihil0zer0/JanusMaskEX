Two brief-authoring lessons hit while completing NGv2 P1.1 (2026-06-21).

**1. Oracles that verify generated code imports/runs MUST use importlib (or subprocess), NEVER `exec`/`eval`/`__import__`.** `harness/ast_enforcer.py::_check_dangerous_calls` (line ~71) bans a `Call` whose `func` is a `Name` in `{'eval','exec','__import__'}` in EVERY generated `.py` — **oracles/test files included** (there is NO tests/** exemption; "tests/** is auto-approved" is a *sensitivity/decision-file* exemption, a DIFFERENT gate). Proven: `validate_code("exec(compile(merged,...))")` → `Violation 'exec() is banned'`; `validate_code(importlib pattern)` → `[]`. The clean pattern to assert "this source string imports without NameError": write it to a temp `.py` under pytest `tmp_path`, then `spec = importlib.util.spec_from_file_location(name, str(p))`, `mod = importlib.util.module_from_spec(spec)`, `spec.loader.exec_module(mod)` — `spec.loader.exec_module(...)` is an `ast.Attribute` call, not the banned `exec` `Name`, so it passes. The NameError surfaces during `exec_module`.
**Why:** a brief that tells an oracle to `exec`/`compile`+`exec` the artifact → both agents emit `exec` → `ast_validation_failed` → `synthesis_or_ast_failed` → wasted dispatch. **How to apply:** when an oracle must execute/import generated code, mandate the importlib `exec_module`-from-`tmp_path` pattern in the brief; forbid bare `exec`/`eval`/`compile`+`exec`/`__import__`.

**2. Keep briefs concise — a verbose multi-line code block can break claude's `plan_draft.json` emission.** The planner spawns claude+gemini to each hand-emit a strict-schema `plan_draft.json` (bash/Python blocked). On an over-long brief claude produced 13187 chars but its draft parsed EMPTY (failed the schema gate); in bootstrap mode the daemon then proceeds with gemini's solo draft → `validate_plan rc=1` (`planner_validation_rejected`); in `--non-bootstrap` it's a loud `PLANNER_LOUD_FAIL_EMPTY_DRAFT`. The same brief planned fine once I condensed the verbose importlib code-block to one prose sentence (373 lines, ~the 309 of a brief that plans reliably). **How to apply:** prefer concise prose over embedded multi-line code in briefs; if the planner rejects, condense before assuming a structural defect. Diagnose with `python -m harness.planner.cli <brief> --non-bootstrap` (full stderr) — the daemon only keeps a truncated `stderr_tail`.

**3. Operational:** restart the daemon child BEFORE editing the allowlist for a new phase — else the still-old daemon picks up the new allowlist, spawns a worker, and the drain on restart kills it → its `.processing` is reaped as orphaned → bounced to blocked/ (recoverable via `.retry.json`, but avoidable). See [[turn-recurring-failures-into-pipeline-fixes]], [[fixes-are-permanent-and-reusable]].

**4. ALWAYS validate a freshly-authored brief with `python -m harness.planner.brief_loader <brief>` (check rc + the `Missing/Empty sections` lines) BEFORE allowlisting.** `harness/planner/brief_loader.py` REQUIRES five sections — `title, scope, inputs, non_goals, deliverables` — matched as EXACT normalized `#`/`##` headers (or frontmatter keys). A trailing parenthetical breaks the match: `# Inputs (VERIFIED against HEAD)` normalizes to `inputs_(verified_against_head)` ≠ `inputs` → `BriefValidationError('Validation failed', missing=['inputs'])` → planner exits **rc=3** in **~0.2s** (pre-agent). The daemon surfaces this only as `planner_validation_rejected ... reason=rc=3` (detail truncated) and then idles — looks like a STALL/"never planned". **Diagnose by rc + wall:** rc=3 wall≈0.2s = brief structural/parse failure (fix the brief headers); rc=1 after ~300s = post-agent `validate_plan` failure (the merged plan). A re-authored brief (newer mtime than the recorded failure) auto-invalidates the deterministic park marker (`autowork_daemon.py:1481`), so just fix + re-validate; no manual park clear needed. **How to apply:** keep required-section headers BARE; move any qualifier into the body. Run brief_loader before every allowlist.

**5. BUILT≠WORKS trap — an oracle can ASSERT the buggy behavior, so a wrong impl passes differential-fuzz.** Hit on nested-symbol patch-apply: the impl fixed only the dotted `Outer.inner` branch and left the 1-part bare-name branch (the REAL production case, e.g. `{'name':'build_evidence'}`) raising; the committed oracle even asserted the 1-part nested case RAISES, locking the bug in, so the impl satisfied a wrong spec and both agents agreed on it. Oracle GREEN ≠ bug fixed. **How to apply:** after any patch-apply/synthesis fix lands, drive the ACTUAL production input through the committed code (a quick analytic script) to confirm WORKS — never trust the oracle alone; and when authoring an oracle, assert the brief's INTENDED behavior, not the current (buggy) behavior. See [[dont-conflate-built-with-works]].
